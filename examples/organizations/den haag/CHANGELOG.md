# Changelog — Den Haag Beslissing Levensonderhoud (ALO) DMN work

History for the `225 Beslissing Levensonderhoud` decision model: why the source
export cannot be deployed, what was derived from it, and the test suite that
backs the result.

Third pass in the series, after
[`../amsterdam/CHANGELOG.md`](../amsterdam/CHANGELOG.md) and
[`../szw/CHANGELOG.md`](../szw/CHANGELOG.md), and deliberately run as a clean
pass: the findings from those two are applied from the start rather than
rediscovered. What was inherited, and what is new, is tabulated in
[`testCases/test-cases-validation-alo.md`](testCases/test-cases-validation-alo.md)
§7.

The model is backed by a live suite covering every rule in every decision —
[`testCases/alo-test-cases.json`](testCases/alo-test-cases.json) (the 65 cases),
[`testCases/test-cases-validation-alo.md`](testCases/test-cases-validation-alo.md)
(the reasoning behind each one, the findings, and how to run them), and
[`testCases/test-cases-alo.sh`](testCases/test-cases-alo.sh) (a self-contained
runner).

## Executive summary

`225 Beslissing Levensonderhoud v3.dmn` decides entitlement to algemene
levensonderhoud bijstand. It is a nine-decision DRD written against a rich
object model (`Zaak` → `Aanvraag` → `Huishouden` → `Personen`), and no DMN
engine can evaluate it.

Where it stands:

1. **Not deployable, for four independent reasons.** Three of its nine
   decisions are `literalExpression`s invoking a decision as a function over a
   filtered collection, with `;` argument separators, `<>` inequality and
   unbalanced parentheses. Six of its nine outputs carry no `name`. Four input
   expressions are empty. Ten cells test `n/a`, which is not FEEL.
2. **Derived, not patched** — `225_Beslissing_Levensonderhoud-patched.dmn`:
   the object model flattened to 26 scalar `inputData`, the reusable person
   decision applied twice as `RechthebbendeAanvrager` / `RechthebbendePartner`,
   and 7 decisions / 55 rules in place of 9 / 42.
3. **The source model could not grant entitlement.** Both of its groen rules
   required a _running_ application, which an earlier rule already refuses. One
   reachable groen rule replaces them.
4. **Unknown is a third value, not a second boolean.** The ten `n/a` cells
   become `"onbekend"` on three-valued inputs, which is what lets
   `informatiebehoefte` name the missing fact instead of reporting only that
   something is missing.
5. **The legal layer is recovered.** All 11 `knowledgeSource` elements and 12
   `authorityRequirement` links are carried across with ids and names
   unchanged. No `cprmv:` cell grounding: these sources carry no `locationURI`
   and name data provenance, not statute, so grounding would mean inventing
   citations.
6. **Two findings recorded without change** — a mixed-household gap that
   matches no rule, and three decisions disconnected from the DRD. Both are in
   the source model; both are policy questions, not transcription errors.
7. **Verified** — 65 cases, one per rule plus boundary, precedence and gap
   cases, all green live. Mutation-checked in every branch, and separately
   verified through the editor's own verdict logic.
8. **Deployed** — `dt225_BeslissingALO` and its six siblings on
   `operaton.open-regels.nl`, via the backend's own `/v1/dmns/deploy` route.
   Backend DMN validation went from 28 warnings and 2 infos to **0 warnings**.
9. **Two superseded files removed** — an earlier `225_Beslissing_Levensonderhoud_deployable.dmn`
   and its `test-cases.json`. They used the same decision ids as the derived
   model, so leaving both in place would mean two models competing for one key
   on a shared engine, whichever was deployed last winning. What they got right
   is carried forward; what they changed or dropped is recorded above.

| 2026-09-10 | dmn-derive, testCases | Derived [`225_Beslissing_Levensonderhoud-patched.dmn`](225_Beslissing_Levensonderhoud-patched.dmn) from `225 Beslissing Levensonderhoud v3.dmn` — 7 decisions, 26 `inputData`, 55 rules — and backed it with 65 live test cases. Nine defects in the source, all fixed: **(a)** three decisions are `literalExpression`s holding object-model expressions no DMN engine evaluates (decision-as-function invocation over a filtered collection, `;` argument separators, `<>` inequality, and unbalanced parentheses in two of the three), which the validator surfaces as 28 `INT-007` warnings for undeclared object-graph roots (`Zaak`, `Aanvraagtype`, `any`); **(b)** six of nine outputs carry no `name` attribute — the Amsterdam blank-exception defect — and a seventh had `name="Reden afwijzing"`, with a space, which is not a usable FEEL identifier; **(c)** four `<inputExpression>` elements are empty, and unlike the SZW case there is no `camunda:inputVariable` to fall back on, so those columns are inert; **(d)** ten cells test `n/a`, which FEEL has no literal for; **(e)** `Om niet`, `Krediethypotheek`, `Verhaalbare bijstand` and `Leenbijstand` appear as bare multi-word FEEL names, and `TekortSchieten`'s first rule tests its own column _label_ rather than a value; **(f)** three cells use `True`/`False` rather than lower-case; **(g)** `RechtOpALO` rules 18–20 are entirely empty, and under `FIRST` rule 18 matches everything not caught earlier and returns nothing; **(h)** its two groen rules both required `Lopende aanvraag of uitkering = true`, which rule 2 already refuses with reden `99`, so **the source model had no reachable path to entitlement at all**; **(i)** the unknown-voorliggende-voorzieningen rule reports `informatiebehoefte` `"datum vorige aanvraag"`, naming a different fact than its column. Resolutions of substance: the object model is flattened to scalars and the reusable person decision applied twice, and every fact that could be `n/a` becomes a three-valued `"ja"/"nee"/"onbekend"` string enumerated in `<inputValues>` — which both restores the six per-fact oranje rules per person and keeps `informatiebehoefte` discriminating (`"verblijfstitel"`, `"detentie"`, `"inkomen"`, `"vermogen"`, `"voorliggende voorzieningen"`) rather than collapsing to a single generic message. Income is the deliberate exception, staying a numeric `maandelijksInkomen < bijstandsNorm` comparison with a separate `inkomenVastgesteld` flag, so the comparison stays in the model. One value is adopted rather than derived and is flagged for Den Haag: the ongeoorloofd-onbetaald-verlof rule has `???` where every sibling has a two-digit reden, and `"04"` is used so the rule is testable. Two findings recorded without change, both present in the source: one person rood with the other groen matches no `RechtOpALO` rule, so the root returns an empty result set (pinned from both sides, and left for Den Haag because what a mixed household is entitled to is policy); and `TekortSchieten`, `DringendeReden` and `HardheidsclausuleToepassen` are required by nothing, so they are covered as their own roots and reported rather than wired in. The legal layer the earlier `225_Beslissing_Levensonderhoud_deployable.dmn` dropped — 11 `knowledgeSource` elements and 12 `authorityRequirement` links — is carried across (the links becoming 18, because the six the source attached to the single reusable person decision appear on each of the two it was split into) — though publishing revealed that the application reads neither construct, so they do not yet reach the exported TTL ([#121](https://github.com/sgort/ttl-editor/issues/121)); preserving them in the DMN remains right, since they are what any future support would read. New: [`testCases/alo-test-cases.json`](testCases/alo-test-cases.json) (65 cases: one per rule across all 7 decisions, with `RechtOpALO`'s 16 driven through `dt225_BeslissingALO` because it passes `redenAfwijzing` and `informatiebehoefte` through, plus three cases evaluating `RechtOpALO` directly, income-boundary pairs, `FIRST` precedence cases and the recorded gap), [`testCases/test-cases-validation-alo.md`](testCases/test-cases-validation-alo.md), [`testCases/test-cases-alo.sh`](testCases/test-cases-alo.sh). All 65 pass live against `operaton.open-regels.nl`; backend validation `valid: true` with **0 warnings** (from 28) and one remaining `EXEC-001` info. |
| 2026-09-10 | tooling               | Fixed a comparison bug in the test runners, found by mutation-checking this suite. `jq`'s `//` is the _alternative_ operator, yielding its right-hand side when the left is null **or false**, so `($act[.key]) // null` turned an actual `false` into `null` and every case expecting a boolean `false` failed against a value the raw response plainly contained (`tekortSchieten(expected=false,actual=null)` beside `"value":false`). Three of this suite's cases hit it — the `false` rule of each judgement decision. It was **latent in [`../szw/testCases/test-cases-pw.sh`](../szw/testCases/test-cases-pw.sh)**, where no case expects a boolean, and would have stayed hidden until one did. Both runners now use an explicit `has()`, which additionally distinguishes an absent key (reported as `<missing>`) from a key that is present and null. The SZW suite still passes 121/121 with the corrected comparison, confirming the fix changed no verdict that was already right.
