# Changelog — SZW PW Normbedragen DMN work

History for the `PW-normbedragen.dmn` bijstandsnorm model: the defects found in
it, the termijnen added to it, the legislative grounding attached to its cells,
and the test suite that backs all three.

Scoped to that model. The other files in this folder — the normenbrief TTL
exports, `SZW_BijstandsnormInformatie.dmn`, `219 Vaststelling Norm v4.dmn` —
predate this changelog and are not covered by it. Same convention as
[`../amsterdam/CHANGELOG.md`](../amsterdam/CHANGELOG.md), which this work

The model is backed by a live test suite covering every norm in every termijn —
[`testCases/pw-normbedragen-test-cases.json`](testCases/pw-normbedragen-test-cases.json)

## Executive summary

`PW-normbedragen.dmn` is a two-decision DRD. `PW_BijstandsnormBedragen` maps a
`peildatum` to a **termijn** and emits all 20 bijstandsnorm amounts for that
half-year at once; `pw-normbedragen` picks the one a caller's `norm` name asks
for and returns it as `bedrag`.

Where it stands:

1. **Termijn added** — `date("2026-07-01") <= date(peildatum) < date("2027-01-01")`,
   all 20 amounts sourced from the CPRMV norms API
   (`?cprmv_version=0.4.1`, `BWBR0015703` @ `2026-07-01`), not transcribed from
   a PDF. This closed a live hole: a `peildatum` in the second half of 2026
   returned `bedrag: null`.
2. **Three defects found and fixed** — `MJK` overwritten with `MJ`'s value in
   two termijnen; two different norms colliding on the `MO` column; seven of
   the 20 columns unreachable because no `norm` value selected them. A fourth,
   a broken DMNDI diagram with a dangling shape reference, fixed alongside.
3. **Amounts independently verified** — 60 of the 100 (termijn × column) cells
   cross-checked against the norms the normenbrief TTLs in this folder already
   publish as `cprmv:Rule` resources. Zero mismatches, and the `MJK` correction
   confirmed by a second source rather than by inference alone.
4. **Cell-level legislative grounding** — 80 cells carry
   `cprmv:sourceQuote` + `cprmv:isBasedOn`, pointing at those same published
   norm URIs. Backend DMN validation went to **zero issues across all five
   layers**, and the generated TTL passes SHACL with **zero errors**.
5. **Two findings recorded without change** — a possible `JO`/`JOK` article
   mis-reading, and a lossy `cprmv:id` in the generator's citation stubs.
   Neither was decided on inference.
6. **Verified** — 121 cases, all green live, covering all 20 norms × all 5
   termijnen plus boundaries, no-match behaviour and regression guards. The
   runner was mutation-checked so a green run means the comparisons ran.
7. **Deployed** — `pw-normbedragen` / `PW_BijstandsnormBedragen` on
   `operaton.open-regels.nl`, via the backend's own `/v1/dmns/deploy` route.

| 2026-09-10 | dmn-grounding      | Implemented Layer 1 of [`../amsterdam/cprmv-cell-level-linking-prototype.md`](../amsterdam/cprmv-cell-level-linking-prototype.md) against this model: `xmlns:cprmv` declared, `cprmv:sourceQuote` + `cprmv:isBasedOn` on **80 cells**, and `cprmv:validFrom` / `cprmv:validUntil` on all five termijn rules. Nothing was minted or guessed — every quote is the `cprmv:situatie` and every citation the subject URI of a norm the normenbrief TTLs in this folder **already publish** as a `cprmv:Rule` (`https://cprmv.open-regels.nl/rules/BWBR0015703_<date>_0_Artikel-…`), and each amount was re-checked against that rule's `cprmv:norm` before its cell was touched. Grounded: the 60 amount cells of the three termijnen whose norm set is published locally (2025-07-01, 2026-01-01, 2026-07-01), plus all 20 norm-name cells of the outer table against the 2026-07-01 set — which is what makes the norm-name-to-legal-situation link machine-readable for the first time. The 40 amount cells of the 2024-H2 and 2025-H1 termijnen are deliberately left ungrounded and carry a `cprmv:note` saying why: no normenbrief rule set for those dates is published here, and their URIs would have to be guessed from the URI pattern rather than read from a source. Deliberately **no bare `dct:source`**: `ttlGenerator`'s CPT path builds `<serviceUri>/concepts/<sourceId>`, which mangles a full URI, and its `pnaWebUri` fallback forces the HvA-specific `hva.pna-web.com` domain — the APT-style quote-plus-citation shape handles full URIs correctly and needs neither. `cprmv:validUntil` is the inclusive last day, matching this repo's own convention in `examples/full-test-import-export.ttl`, and lines up exactly with the suite's TC111–TC114 day-before cases. Verified end to end: backend DMN validation **0 issues in all five layers** (`EXEC-001` cleared); `dmnHelpers.extractRulesFromDMN` reads all 80 groundings; `ttlGenerator` emits 80 `cprmv:Rule` cell resources inside their rules' `cprmv:hasPart` plus 36 deduplicated citation stubs; the generated Turtle passes SHACL with **0 errors**; and all 121 test cases still pass against a fresh deployment, confirming the grounding is behaviourally inert. One finding recorded, not fixed: the citation stub emits `cprmv:id "<the full URI>"` because the generator has no other identifier for an external target, whereas these URIs are ours and the normenbrief graph gives them a real `cprmv:id` (`"onderdeel a."`). Harmless but lossy — `ttlGenerator` could skip the stub for an already-typed `cprmv.open-regels.nl` rule URI, or derive the id from the last `ruleIdPath` segment. Tracked as [ttl-editor#116](https://github.com/sgort/ttl-editor/issues/116). |
| 2026-09-10 | dmn-fix, testCases | Added the 2026-H2 termijn (`date("2026-07-01") <= date(peildatum) < date("2027-01-01")`) with all 20 amounts taken from the CPRMV norms API (`BWBR0015703` @ `applicable_date: 2026-07-01`) rather than a normenbrief transcription — closing a live hole where any `peildatum` in H2 2026 answered `bedrag: null`.
